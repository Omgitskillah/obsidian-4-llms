# obsidian-mcp

An MCP server exposing access to an Obsidian vault: browsing, searching, reading, and writing notes, plus tag data and the link graph.

## Setup

The server's settings live in `.env.obsidian` in the repo root (see [Settings](../../README.md#settings)). From the root, copy the template and set `VAULT_PATH` to your vault's absolute path:

```bash
cp .env.obsidian.example .env.obsidian
# then edit .env.obsidian
```

```
VAULT_PATH=/absolute/path/to/vault
```

Install dependencies and run:

```bash
uv sync
uv run obsidian-mcp
```

This starts the server over stdio and waits for a host (e.g. Claude Desktop) to connect - see the [servers README](../README.md) for running it, testing it with the MCP Inspector, and access logging.

## Dependencies

- **`mcp`** - The MCP server framework this package is built on (`MCPServer`, `@mcp.tool`, `@mcp.resource`); required to expose these tools/resources to a client at all.
- **`python-dotenv`** - Loads `VAULT_PATH` (and `OBSIDIAN_MCP_LOG_DIR`) from the root's `.env.obsidian` at startup, so the vault location isn't hardcoded or passed as a CLI flag.
- **`access-logging`** (workspace package, see [servers/tools/logging](../tools/logging)) - Provides `AccessLogMiddleware`, which logs every session's tool/resource access under `.logs/` regardless of which client connects. Shared across servers in this repo rather than reimplemented here.
- **`python-ulid`** - Spec-correct ULID generation for note ids. Chosen over a hand-rolled implementation so the ID format (timestamp + randomness, base32 encoding) is backed by a maintained library instead of custom code.
- **`pyyaml`** - Serializes a new note's frontmatter, rather than string-templating it, so key ordering, block-style lists, and quoting (e.g. a value starting with `{` being read back as a flow mapping) are handled correctly.
- **`unidecode`** - Transliterates a title to ASCII before slugifying it, so accented Latin letters and non-Latin scripts (CJK, etc.) survive into the filename as a readable approximation instead of being silently dropped.
- **ripgrep (`rg`)** - Not a Python package: a binary that has to be on the `PATH` the server is launched with (`brew install ripgrep`; a GUI host such as Claude Desktop may not have Homebrew's `/opt/homebrew/bin` on its own `PATH`). `find_in_notes` runs it for the search and reads each match's line number and position from its `--json` output. Without it that one tool raises `FileNotFoundError` (naming `search_notes` as the fallback); every other tool is unaffected.
- **`sqlite-vec`** - The vector store behind `semantic_search`: a SQLite extension loaded into the stdlib `sqlite3`, so the index is one file and there's no separate server process. A single wheel with no dependencies of its own; pre-1.0.
- **Ollama with `nomic-embed-text:v1.5`** - Not a Python package: `semantic_search` and `obsidian-mcp-index` embed text through the local Ollama's HTTP API (stdlib `urllib`, no extra client). `ollama pull nomic-embed-text:v1.5` once. Every other tool works without it.

## Note model

Notes created by `write_note` are **append-only**: their frontmatter is written exactly once, at creation, and is never rewritten. `id`, `created`, `path`, `tags`, and `aliases` are all server-owned - the caller cannot set them directly. There is no whole-file overwrite (`replace_content`): the only way to change an existing note is `write_note` again, which can only add to the body.

An index (`.obsidian-mcp-index.sqlite3`, a dotfile inside the vault so it never shows up in `browse`) records `id -> path/type/title/author/created/supersedes` for every note `write_note` has created. It exists to give each note an id and to validate `supersedes` and `targets` without scanning the vault - it only knows about notes `write_note` created, not ones added directly in Obsidian. The file write and the index insert are treated as one operation: if the index insert fails, the just-written file is deleted rather than left as an orphan the index doesn't know about.

The index only learns about a filesystem change through this server's own tools - it has no way to notice the vault changing any other way (Obsidian sync, a git pull, a note deleted directly in the UI, the whole vault cleared out from under it). Left unreconciled, a stale row (its file gone, but its path still `UNIQUE`-constrained) can make a legitimate create collide with a path that no longer exists on disk. So every time the index is opened, it's first reconciled against the current filesystem: any row whose path no longer exists is dropped. There's no separate "startup" hook in this long-running process to do this once, so it runs on every open instead - simple, and correct regardless of when or how the vault changed. `rename_or_move_file` opens (and so reconciles) the index *before* physically moving the file, specifically so reconciliation can't see the old path already gone and delete the row out from under the repoint that's about to happen.

`rename_or_move_file` keeps this index in sync: moving an indexed note - including into `archive/` or `trash/` - repoints its row to the new path (rolling back the move if that repoint fails). Moving a file the index has no row for (an attachment, say) is a no-op on the index, not an error.

The template itself - what fields exist and their allowed values - lives in [`frontmatter_template.py`](src/obsidian_mcp/frontmatter_template.py), separate from `server.py`'s tool logic, and is a plain Python module (not an editable data file) on purpose: the whole point of versioning it is that nothing changes its shape without a code change and a version bump alongside it.

The eleven `type`s a new note can have (`template.TYPE_FOLDER`) each map to a fixed folder:

| Folder | Types |
|---|---|
| `user/` | `directives` (Nuru never writes there) |
| `nuru/` | every other type, by default - since template `0.4.0` a folder is only the default: a new note may go in any folder under `nuru/` or `shared/` |

`author` must be one of `user`, `nuru`, `both` (`template.VALID_AUTHORS`). Some types take exactly one extra field (`template.TYPE_FIELD`), passed as its own named parameter: `date` (`daily`), `targets` (`correction`), `session` (`transcript`, `session`) - e.g. `write_note(note="Standup", type="session", ..., session="2026-09-14-01")`. `targets` is required, since only the caller knows what is being corrected. `date` and `session` are not: left out, `date` defaults to today (and `write_note` only ever makes today's daily) and `session` to today's next unused `YYYY-MM-DD-NN` for that type, so a caller doesn't have to state (or get wrong) today's date or work out which session number is free. "Next unused" is one past the highest `NN` any note of that type already has today - not the first gap, so a later session never sorts before an earlier one - and it is counted per type, so a transcript and the session note for the same conversation are both `-01`. The defaults apply only when no extra field was passed at all; a wrong field (a `session` on a `daily`) still fails with an accurate error. "Today" is the server's clock, the same one `created` uses. This is a deliberate loosening of the earlier "exactly the required field must be passed" rule, made because these were the fields a small model most often got wrong or omitted; it changes no note's shape, so `template.VERSION` is unchanged. These are explicit parameters, not `**kwargs`: a `**kwargs` catch-all is exposed in the MCP tool schema as a single required string field no caller can satisfy, which made note creation uncallable through any MCP client until this was fixed.

Every note's frontmatter carries a `version` field, stamped from `template.VERSION` at creation and never touched again. Because notes are append-only, this is the only way to know which frontmatter structure an existing note was written under once that structure changes - so `template.VERSION` gets bumped (semver) whenever `frontmatter_template.py`'s shape changes, or `server.py`'s `_build_frontmatter` output shape changes (a field added/renamed/reordered), but never bumped retroactively: an old note keeps the version number that was current when it was actually written. A future tool that reads notes back can branch on `version` to handle older structures correctly instead of assuming today's shape everywhere.

`frontmatter_template.py` carries the authoritative definition of what each version number means - a `version` isn't just an incrementing counter, it's a key into that table. **`0.1.0`** (current) means exactly: field order `id, version, type, created, author, supersedes, [<type-specific field>], tags, aliases`; `id` a ULID minted once and never touched again; `created` `"YYYY-MM-DDTHH:mm"` server clock; `author` one of `user`/`nuru`/`both`; `supersedes` an existing note's id or blank; the type-specific field (present only for types in `TYPE_FIELD`) validated per its own rules (`date`: `"YYYY-MM-DD"`; `session`: `"YYYY-MM-DD-NN"`; `targets`: a list of existing note ids); `tags` a block list of `[type, ...extra]` with no tag containing whitespace; `aliases` a block list of `[title, id]`.

**Not yet implemented** (deferred from the original spec, to keep each change independently reviewable): `read_note` returning ids instead of paths (`search_notes` now returns each hit's id alongside its path, and `read_note` now accepts an id as its `name`). Archive-by-move (replacing a `status: archived` field, which append-only rules out) is `rename_or_move_file(name, "archive")`.

### Finding, naming and following notes

`browse`, `tags`, `read_note` and `note_info` exist so a small model can orient itself and follow the vault instead of guessing `search_notes` queries.

**Ordering.** `browse` and `tags(tag=...)` list newest first. "Newest" is the index's `created` for a note `write_note` created, and the file's modified time for any other note - a note typed in Obsidian has no `created` the server can trust. Both are local time in the same `YYYY-MM-DDTHH:MM` format, so the two kinds sort together. A note `write_note` created is *not* ordered by modified time, so appending to an old daily doesn't make it "the latest daily". `created` only goes to the minute, so notes made in the same minute are ordered by their ULID id, which sorts by creation time to the millisecond. One exception: with `type` set to `daily`, `transcript` or `session` (the types that carry a `date` or `session` field), notes are ordered by that field instead, because "the latest daily" means the latest *date* - a daily backfilled today is still older than yesterday's real one. Without a `type`, the mixed list stays in created/modified order. A non-indexed note has a `null` id and its filename as title (`write_note` still reaches it by path); its `type` is whatever its own frontmatter says, which is what lets a daily made in Obsidian from a `Templates/` file show up under `browse_notes(type="daily")`.

**Working set.** Every tool that lists, searches, reads or resolves notes skips `Templates/`, hidden folders (`.obsidian`, Obsidian's `.trash`), symlinks that resolve outside the vault, and `trash/` - a trashed note is gone as far as any tool can tell. `archive/` is part of the working set: an archived note is still browsed, tagged, searched, read, linked and embedded; it just can't be written to (see *Archive and trash*).

**Tags.** `tags` reads the frontmatter `tags` list as well as inline `#tags`. That matters: `write_note` writes every tag (including the type tag) only into frontmatter, so a scan for `#tag` alone would find none of the notes this server made. Tags are lowercased (Obsidian treats them case-insensitively), `notes_with_tag("project")` also matches nested `project/alpha`, `all_tags` counts *notes* per tag (matching what `notes_with_tag` returns for it) rather than occurrences, and a tag that matches nothing gets a "did you mean" hint from the tags actually in use. The `vault://tags` resources are unchanged and still count `#tag` occurrences only; the tools exist because a client that only calls tools can't read resources.

**Name resolution.** `read_note`, `note_info`, `write_note` and `rename_or_move_file` resolve a note's name the same way. Tried in order: as a vault-relative path; as a filename anywhere in the vault (first match alphabetically, as before); then forgivingly, comparing slugs - so case, punctuation and spacing don't matter - first against the note's whole path, then its filename, then its titles, aliases and ids (the index's title and id, and the frontmatter's `aliases` and `id`; `write_note` writes a new note's title and id into `aliases`, so a title or an id finds the note). A wrong or missing folder in front of the right name still finds it. No tier ever matches into `Templates/`, `trash/`, hidden folders or outside-the-vault symlinks. The forgiving tier reads every note, so it only runs when the exact tiers find nothing. On a miss `read_note` still raises `FileNotFoundError` - a hint returned as ordinary text couldn't be told from the note's own content, which is the reason a miss was never an empty string either - but the message now names the three closest notes by filename/title and points at `browse_notes`/`search_notes`. `write_note` and `rename_or_move_file` refuse a name that matches several notes (the same filename in two folders, two notes sharing an alias) instead of taking the first, since a forgiving lookup that guesses wrong would change the wrong note.

**Sections.** `read_note(name, section="Decisions")` returns one heading through to the next heading of the same or a higher level, so its own subheadings stay in. The match ignores case, extra whitespace and leading `#`s. A `#` line inside frontmatter or a fenced code block is not a heading. An unknown section raises `ValueError` listing the note's real headings.

**Links.** `note_info(name)`'s links part (the internal `get_links`) returns `{note, outgoing, backlinks}`. `outgoing` is each distinct `[[wikilink]]` target (the `|alias`, `#heading` and `#^block` parts are dropped; an embed counts) resolved to a path by the rule above - so `[[id]]` links, which the `directives` template asks for ("Link by `id`"), resolve - or `null` when no note has that name. `backlinks` is every other note that links here, by any of those forms. Each list is capped at 25 with a hint. Backlinks are found by building the name tables once and resolving every link in the vault by dictionary lookup, not by walking the filesystem per link.

**Broken links.** No longer a tool (2026-10-02): to become a system job that fixes or flags broken links on its own. The internal `find_broken_links()` is the whole-vault form of `get_links`' null paths, in one call: every `[[wikilink]]` whose target resolves to no note by the rule above, and isn't the filename of an attachment in the vault (`![[diagram.png]]`). It returns `{count, links}`, `links` being `{path, link, line}` by path then line, each link once per note at the line it first appears on, capped at 25 with a hint. It exists because answering "which links are broken?" with `find_in_notes` and `get_links` took a small model one call per note (eval test 6, 2026-09-29).

**Line search.** `find_in_notes(pattern)` is the line-level counterpart of `search_notes`: that ranks notes containing every word somewhere, this shows the exact lines a regular expression hits - for an id, a number, a phrase, a snippet of code. It runs `rg --json` and returns `{pattern, count, matches}`: at most 10 notes in path order, each `{path, lines}` with at most 5 `{line, text}`; `count` is the total number of matching notes and a `hint` explains an empty or cut-off result. A note with more than 5 matching lines is told from one with exactly 5 by asking ripgrep for one line more than is shown (`--max-count 6`). A line longer than 120 characters is cut to a window around the match - a Markdown paragraph is a single line, and a match deep in one would otherwise be missing from what the model sees. The pattern is a regex in ripgrep's syntax, matched case-insensitively against one line at a time (frontmatter lines included). Small models escape badly, so: `literal=true` matches the pattern as plain text (`--fixed-strings`), with nothing to escape; a pattern ripgrep rejects as a regex (`[[`, an unclosed bracket) is searched again as plain text, the hint carrying ripgrep's message; and a pattern with a double backslash that matches nothing (`\\[\\[`, a literal backslash before each bracket) gets a hint saying so. Only when the plain-text search fails too does it raise `ValueError`.

Which notes count is not left to ripgrep: its `*.md` matches are intersected with `_all_notes()`, the same set every other tool reads, so `Templates/`, `trash/`, hidden folders and symlinks out of the vault never show up, while `archive/` does, as in `search_notes`. ripgrep is also called defensively: `--no-ignore` (a `.gitignore` in a vault kept under git would otherwise hide notes from the search), `--no-config` (a user's `RIPGREP_CONFIG_PATH` could change the output this parses), stdin closed and an explicit search root (given neither, and a piped stdin, ripgrep searches stdin - here the MCP transport), and the pattern passed as `-e <pattern>` so a model-supplied `--pre=...` can never be read as an option. It gets the same 10-second deadline as the writers, raising `TimeoutError`.

**Archive and trash.** `rename_or_move_file(name, "archive")` or `(name, "trash")` moves the note into that folder under its own folder path (`nuru/x.md` -> `archive/nuru/x.md`) and returns `{from, to}`; an archived note going to trash drops its `archive/` prefix. The filename never changes, so `[[links]]` to an archived note keep resolving, and the note keeps its id and index row. **Archive** keeps a note visible but read-only: `write_note` refuses it, naming the `rename_or_move_file` call that moves it back out, after which it can be written again. A note already under `archive/` can't be archived again. **Trash** is a delete as far as any tool can tell: nothing in `trash/` is listed, searched, read, resolved, linked or embedded, writing to a trashed note's title makes a new note, and nothing can be moved out of `trash/` - emptying or restoring it is for a person, in Obsidian. Both inherit `rename_or_move_file`'s boundaries: nothing under `user/` (`directives`, `daily`), nothing in a hidden folder, no overwriting an existing file, and, for Nuru's own server, nothing the user wrote.

**Writing: `write_note`.** One tool creates and writes, so the model never has to decide whether a note exists first. `type="daily"` writes to Nuru's own daily note for today, in `nuru/` (template `0.3.0`: dailies moved out of `user/`), and creates it if missing - no date, title or id needed; reminders go there too. The user's own dailies in `user/` are never written. An existing daily is found by its frontmatter (`type: daily` and `date` equal to today), not by guessing a filename, because a daily made in Obsidian can be named anything - and so one made in Obsidian is appended to instead of duplicated. A new one is titled `Daily YYYY-MM-DD` (file `nuru/daily-YYYY-MM-DD.md`), author `nuru`; if that filename is already taken by a note that isn't recognisable as a daily, it fails with `FileExistsError` rather than overwrite it. Otherwise `note` is resolved by name (above): one match is appended to; several are refused; none creates a new note titled `note`, which then needs `type` and `author`. Three guards stop a write landing in the wrong place: a `note` that looks like a path or an id (contains `/`, ends `.md`, or is 26 uppercase letters and digits, so a mistyped id counts) but matches nothing is refused with the closest notes, rather than quietly becoming a duplicate's title; an existing note is never appended to with `supersedes`, `targets` or a `type` other than its own, so a correction can't turn into an edit of the note it corrects; and an archived note is refused.

### Template files (`Templates/`)

`Templates/` holds the skeleton files Obsidian's own "Insert template" uses. No tool writes there any more (`generate_templates` was retired, 2026-10-02); every read tool skips it, so a placeholder skeleton is never mistaken for a note.

## Semantic search

`search` matches words first and meaning second, and `find_in_notes` matches lines; the meaning half (the internal `semantic_search`) is what makes a question about a "car" find a note about servicing the "automobile". It sits after the exact matches rather than replacing them - an exact id, name, date or number is still a job for the word match or `find_in_notes`. The code is in [`semantic.py`](src/obsidian_mcp/semantic.py).

**How it works.** Each note is split into passage-sized chunks, each chunk is embedded by `nomic-embed-text` v1.5 running in the local Ollama, and the vectors are stored with the chunk's text, the note's path and its id in `.obsidian-mcp-semantic.sqlite3` - a dotfile in the vault, like the note index, so the listing tools never show it. Nothing leaves the machine and nothing secret is stored: only note text and its vectors. v1.5 rather than v2 because v2's 512-token limit would force much smaller chunks. nomic's task prefixes are added for you (`search_document: ` for a chunk, `search_query: ` for a query) - retrieval is noticeably worse without them.

**What's indexed.** Every note except `Templates/`, `trash/`, hidden folders and symlinks out of the vault - the same working set `browse` shows, `user/` and `archive/` included. No other folder name is assumed, so the vault can be reorganised freely. A note's id is the one `write_note` gave it, else its frontmatter `id`, else `null`.

**Building the index.** Nuru keeps it current on its own: while Nuru runs, a background thread (see [`vault_indexer.py`](../../nuru/src/core/vault_indexer.py)) looks over the vault every 30 seconds and embeds whatever changed, and the window title reads `Nuru ⠹ indexing 12 notes` while it works - held for at least 1.5 s, then `Nuru · indexed 12 notes` for 3 s, since re-embedding one note takes ~0.1 s. Every pass that changes the index also prints a line to the terminal Nuru was started from (`Nuru: semantic index - indexed 1 note: user/daily-2026-09-17.md`) and adds an `index_pass` event to Nuru's session log under `nuru/logs/`. The first time, that means the whole vault. To build or update it by hand - for another client such as Claude Desktop, or to get the first build out of the way:

```bash
ollama pull nomic-embed-text:v1.5   # once
uv run obsidian-mcp-index            # embeds new and changed notes
uv run obsidian-mcp-index --rebuild  # starts over - needed after changing either knob below
```

Updates are incremental. A note whose modified time hasn't changed isn't read; one whose content hash hasn't changed isn't re-embedded; a deleted or trashed note is dropped. A note moved to another folder keeps its vectors under its new path, unless its title changed too (the title heads every chunk, so a renamed note is re-embedded). Each note's chunks are replaced in one transaction, so a search never sees half a note and an interrupted build resumes where it stopped. The database runs in WAL mode, so the server can search while Nuru writes.

**The two knobs to tune** once a first index exists, both set in `.env.obsidian`:

| Variable | Default | |
|---|---|---|
| `OBSIDIAN_EMBED_MODEL` | `nomic-embed-text:v1.5` | The embedding model. The explicit `:v1.5` tag matters: plain `nomic-embed-text` means `:latest`. |
| `OBSIDIAN_CHUNK_CHARS` | `1500` | The most characters of a note in one chunk, about 350-400 tokens - enough for a whole passage, small enough that five results fit in a small model's prompt. At least 200. |
| `OBSIDIAN_SEMANTIC_DB` | `<vault>/.obsidian-mcp-semantic.sqlite3` | Where the index lives. |
| `OLLAMA_HOST` | `http://localhost:11434` | Ollama's own variable. |

The index records which model and chunk size built it and refuses to mix: vectors from different embedders aren't comparable, and a mix of chunk sizes skews scores. After changing either, `semantic_search` and the indexer raise `ValueError` until you run `--rebuild`.

**Chunking.** Frontmatter is left out. Each heading starts a new chunk, so a chunk is (part of) one section; within a section, paragraphs are packed together up to `OBSIDIAN_CHUNK_CHARS`, a longer paragraph is split between sentences, and a single sentence longer than that is cut. A fenced code block stays together, and a `#` line inside it isn't a heading. Every chunk starts with a label line, `Title > Section`, so it still says what it's about when read on its own - by the embedder or by the model. Headings with nothing under them make no chunk.

**Context length.** Ollama serves this model with `num_ctx 8192`, but `ollama show nomic-embed-text:v1.5` reports the GGUF's context length as 2048. With 1500-character chunks that doesn't matter. The indexer calls Ollama with `truncate: false`, so a chunk that ever did exceed the limit fails loudly instead of being indexed by only its first part.

## Security

All path-taking tools (`browse` with a folder, `read_note`, `note_info`, `write_note`, `rename_or_move_file`) are confined to `VAULT_PATH`: `..`/absolute-path traversal is rejected, and a symlink stored inside the vault that points outside it is also rejected (checked against its resolved, real location, not just its name). A new note's path is server-derived (`type` folder + slugified title), never caller-supplied, so it goes through the same containment check but can't be steered outside the vault by input.

`rename_or_move_file` additionally refuses to touch anything inside a dotfile/dot-directory (`.obsidian/`, this server's own `.obsidian-mcp-index.sqlite3`) - the listing tools already excluded these from what they *show*, but that was cosmetic: nothing previously stopped a structural tool from reaching in and moving `.obsidian/app.json`. There is no delete tool at all (`delete_file_or_directory` was retired, 2026-10-02): a delete is a move to `trash/`.

**Corrections** (template `0.2.0`, 2026-09-29). A correction used to be the user's alone, in `user/`. It now lives in `nuru/` and any author may make one, so Nuru can correct a note without touching it: `write_note(note="<new title>", type="correction", author="nuru", targets=[<ids>])` opens its body with `Corrects: [[<id>]], ...`, linking every corrected note by id - so the correction shows in their backlinks, and the link survives a rename or an archive. Notes made under `0.1.0` stay where they are.

**Corrections, 2026-10-03.** The small model couldn't manage a separate correction note with `targets` (eval runs 21, 23, 521, 718), so: a note Nuru may edit - in `nuru/`, not written by the user - is fixed in place with `mode="replace"` (the old version is kept in `trash/`); anything else (a note the user wrote, anything in `user/`, a joint note in `shared/`) gets a short correction note whose content links `[[the note]]`, and the server takes its `targets` from those links.

### Permissions

`rename_or_move_file` - so archive and trash too - refuses to touch anything under `user/` (`directives`, `daily`). Only `write_note` can write there (creating a `user/` type with author `user`, appending to today's daily, or appending to a note already there), so nothing can move a boundary-setting note out from under it.

Archived notes can't be written by anyone (`write_note` refuses them for every client), and nothing can be moved out of `trash/` - both enforced here in the server, not only in Nuru.

**Notes the user wrote, outside `user/`.** When the server runs with `OBSIDIAN_PROTECT_USER_AUTHORED=1` - Nuru sets it for its own server process - `write_note` and `rename_or_move_file` (so archive and trash too) also refuse any note outside `user/` whose frontmatter says `author: user`, with a `PermissionError` that points at writing a correction instead. Inside `user/` the folder rules above apply as before, so `write_note(type="daily")` still appends to today's daily. Other clients (Claude Desktop, the Inspector) leave it unset: there a person is choosing what to change. A note with no `author` in its frontmatter isn't covered - "written by the user" is only what the frontmatter says.

This is a narrow slice of the permission model the original design called for, not the whole thing: there's no notion here of *who* is calling (a human's explicit instruction vs. an autonomous decision), so it can't enforce "Nuru read-only" in the fuller sense that implies - it only enforces "no tool but `write_note`, regardless of caller, can touch `user/`". `write_note` remains free to write there, since blocking it would break every `user/`-folder note type's ability to be created or grown at all.

## Reliability

Both filesystem-mutating tools (`write_note`, `rename_or_move_file`) run their actual disk I/O through a small thread pool with a 10s deadline. If the underlying filesystem call stalls (an unavailable network mount, a stuck disk), the tool raises `TimeoutError` immediately instead of leaving the caller hanging - Python has no safe way to forcibly kill a thread stuck in a blocking syscall, so the abandoned worker thread is left to finish (or never does) rather than cancelled.

Because of that, creating a note uses an atomic exclusive-create (`open(path, "x")`) rather than a separate exists-check-then-write: a client retrying an identical create after a timeout is safe even if the original, abandoned write is still landing - the two can't silently race and clobber each other, and the retry still correctly fails with `FileExistsError` if a note is already there.

## Error handling

Every tool is wrapped (`@_tool` in `server.py`) so its own anticipated failures - bad input, not found, already exists, permission denied, a timed-out write, Ollama not running (`ValueError`, `FileNotFoundError`, `FileExistsError`, `PermissionError`, `TimeoutError`, `ConnectionError`) - reach the caller as `ToolError` with the original exception's type and message intact. Without this, the MCP framework only forwards a raised exception's message to the client for `ToolError` (or a subclass); anything else is treated as a crash and replaced with a bare `Error executing tool <name>`, discarding the message entirely - every failure this server raises looked identical from the outside. A genuinely unexpected exception (a real bug, not one of the six types above) still gets that generic treatment, which is the correct behavior for something truly unanticipated.

`read_note` raises `FileNotFoundError` for a missing note rather than returning an empty string, which was indistinguishable from a note that's genuinely empty. A note whose frontmatter isn't valid YAML (easy to produce by hand in Obsidian, including an impossible date like `2026-13-45`) is read as having none, rather than failing every tool that scans the vault.

## Tools

- **`browse(type=None, limit=10, folder=None)`** - Replaces `list_notes`, `list_files`, `list_files_in_directory` and `browse_notes`. List notes newest first, each `{path, id, type, title}`, optionally only one `type` (an unknown type raises `ValueError`; a blank one means no filter). `limit` is at least 1 and capped at 50, so this can't turn back into a whole-vault dump. Returns `{count, notes}` with `count` the total that match, plus a `hint` for an empty or cut-off result. Answers "what's my latest daily": `browse_notes(type="daily")`. See *Finding, naming and following notes* for how "newest" is decided and what's excluded. With `folder` - a vault-relative path, or a folder name found anywhere in the vault (first match alphabetically) - only notes under that folder, recursively, count, and the result adds `folder` (the resolved path) and `files`: its other files (attachments), at most 25. A folder that doesn't exist, is outside the vault, a symlink pointing out of it, or `trash/` gets an empty result and a `hint`.
- **`tags(tag=None, note=None)`** - Replaces `all_tags`, `notes_with_tag` and `note_tags`; which one runs depends on the argument, and passing both is refused.
  - *No arguments* (was `all_tags`): Every tag in use with the number of notes carrying it, most-used first (at most 25, with the true `count`), from frontmatter and inline `#tags`. Returns `{count, tags}`.
  - *`tag`* (was `notes_with_tag`): The notes carrying `tag` (any case, leading `#` optional; a parent tag matches nested ones), newest first, at most 10 with the true `count`, each `{path, id, type, title}`. A tag that matches nothing gets a hint with the closest real tags.
  - *`note`* (was `note_tags`): One note's tags, from its frontmatter `tags` and inline `#tags`, lowercased and sorted (the same reading as `all_tags`). Returns `{note, tags}`. `name` as for `read_note`.
- **`search(query)`** - Find notes: exact word matches first, then notes found by meaning, at most 10 notes in all and one entry per note (a note already matched exactly isn't repeated, and only a note's best passage is kept). Each match says how it was found: `match: exact` with a `snippet`, or `match: meaning` with the passage `text` and its `score`. Returns `{query, exact_count, matches, hint}`; `exact_count` is how many notes contain every word. If the meaning half can't run (no index yet, another model's index, Ollama not running) the exact matches still come back, with a hint saying why. Excludes `Templates/` and `trash/`.
  - *Exact half* (what the `search_notes` tool was; now internal): Search notes by content, title and filename. `query` is one or more whitespace-separated words: every word must appear (in the note's content, title or filename, in any order, ignoring case). Inside a word, `-` and `_` also match each other and a space, and the parts must sit side by side: `PDP-drop` finds `PDP_drop` and `PDP drop`, and `09-17` finds `2026-09-17` but not a note that merely mentions 09 and 17 separately (written `09 17`, those are two words and may be anywhere) - so date and id searches stay as precise as a literal substring match. Returns `{query, count, matches}` with `matches` holding at most 10 hits, best first (a note with query words in its filename or title ranks above one that only matches in the body; ties are broken by path), each `{path, id, type, title, snippet}`. `count` is the total number of matches, which can exceed 10. `id`/`type`/`title` come from the index, so a note `write_note` didn't create has `null` `id` and `type` (and its filename as `title`) - `write_note` reaches it by path. `snippet` is about 120 characters of the body, frontmatter skipped, around the first hit. A `hint` says how to retry when nothing matches, or how to narrow when results were cut off; a query with no words raises `ValueError`. Returns a dict rather than a bare list so an empty result still reaches the model as a readable message instead of a blank tool response. Only reads the index if it already exists, so searching never creates it.
  - *Meaning half* (what the `semantic_search` tool was; now internal, asked for 10 passages, each cut to 400 characters in `search`'s result): The passages nearest in meaning to `query`, for a question or an idea when you don't know the note's words. `top_k` is at least 1 and capped at 10. Returns `{query, matches}`, best first, each `{path, id, text, score}`: `text` is the chunk (headed `Title > Section`), `score` the cosine similarity (1 is closest), `id` `null` for a note without one. A `hint` explains an empty result. Only reads the index (see *Semantic search*), so a note edited in the last few seconds may still be found by its old text. Raises `FileNotFoundError` if no index has been built, `ValueError` for an empty query or an index built with another model or chunk size, `ConnectionError` if Ollama isn't running. Excludes `Templates/` and `trash/`.
- **`find_in_notes(pattern)`** - Find the lines of notes matching a regular expression (ripgrep syntax, case-insensitive) - for an exact phrase, id, number or code, where `search_notes` matches words. Returns `{pattern, count, matches}`: at most 10 notes in path order, each `{path, lines: [{line, text}]}` with at most 5 lines (`line` is 1-based; `text` is cut to about 120 characters around the match). `count` is the total number of matching notes, and a `hint` explains an empty or cut-off result. Excludes `Templates/`, `trash/`, hidden folders and symlinks out of the vault; includes `archive/`. An empty pattern or one ripgrep rejects raises `ValueError`; `rg` not being installed raises `FileNotFoundError`. See *Line search* under *Finding, naming and following notes*.
- **`read_note(name, section=None)`** - Return a note's contents by name: a path, a filename (with or without `.md`), or - forgivingly - a title, alias or id in any case (see *Finding, naming and following notes*). An exact path or filename is tried first, and the first match alphabetically wins if a filename appears in several folders. `section="Heading"` returns just that heading through to the next of the same or higher level; blank or omitted returns the whole note. Raises `FileNotFoundError`, naming the three closest notes, if none matches; `ValueError`, listing the note's headings, if `section` isn't one of them.
- **`note_info(name)`** - Replaces `get_links` and `note_todos`, and adds the note's tags (as `tags(note=...)`): everything around one note except its text, which stays with `read_note`. The name is resolved once and every part describes that note. Returns `{note, tags, outgoing, backlinks, todos, todo_count, hint}`.
  - *Links* (was `get_links`): A note's outgoing `[[wikilinks]]` resolved to paths (`null` where no note has that name) and its backlinks. Returns `{note, outgoing, backlinks}`, each list capped at 25.
  - *Open tasks* (was `note_todos`): One note's open tasks: every unticked checkbox (`- [ ]`, `* [ ]`, `1. [ ]`) and every line containing `TODO`, with 1-based line numbers. Ticked `[x]` items, frontmatter and fenced code blocks are skipped. Returns `{note, count, todos: [{line, text}]}`, at most 25, with a `hint` for an empty or cut-off result.
- **`write_note(content="", note=None, mode="append", type=None, author=None, tags=None, supersedes=None, targets=None, session=None)`** - Write to a note, creating it first if it doesn't exist (see *Writing: `write_note`*). `type="daily"` is Nuru's own daily note for today, in `nuru/`. Otherwise `note` is an existing note's path, title or id; or, for a new note, a title (it goes in `nuru/`) or a path under `nuru/` or `shared/` such as `nuru/People/Dana Lee` (folders are made as needed). A new note may be empty; `type` defaults to `topic` (the description lists what each type is for, from `TYPE_DESCRIPTIONS`) and `author` to `nuru`. A type given for an existing note is ignored, except `correction`, which is refused. A new note whose name is all but an existing one's (`_near_names`; names differing only in digits don't count) is refused with "did you mean". An append whose content contains the note's own text is refused, pointing at `mode="replace"`. `mode="append"` (the default) adds `content` to the end, with a blank line before it; `mode="replace"` makes `content` the note's whole text after its frontmatter, which is kept - the one way to change existing text, so every guard applies to it too. On Nuru's server only notes in `nuru/` can be replaced; the version a replace overwrites is copied to `trash/<path>.<timestamp>.md` first (invisible to every tool, recoverable in Obsidian); text identical to the note's changes nothing and `done` says so; replacing with nothing is refused (a delete is a move to trash). Creating validates as the Note model describes. Refuses an ambiguous `note`, a path or id that matches nothing, creation-only arguments on an existing note, an archived note, and - on Nuru's server - anything under `user/` and any note the user wrote. A correction (`type="correction"`) needs no `targets`: if left out they are taken from the `[[links]]` in its content, and one that links no note is refused. Returns `{done, path, id, created}`: `done` is one sentence naming the note, its path and what was done.
- **`rename_or_move_file(source_path, destination_path)`** - Move a file, repointing its index row if it's an indexed note (see Note model above). `source_path` is a vault-relative path or, for a note, any name `read_note` accepts (a name matching several notes is refused). `destination_path` is the new vault-relative path, or just `archive` or `trash` to move it there under its own folder path (see *Archive and trash*). Returns `{from, to}`. Raises `FileNotFoundError` if the source doesn't exist, `FileExistsError` if the destination already does, `ValueError` for a note already archived, or `PermissionError` for a source in `trash/`, a path that is hidden (e.g. `.obsidian/`) or under `user/`, or a user-written note when that protection is on (see Permissions above).

Not implemented: patching content near a heading, block reference, or frontmatter field (an atomic/surgical insert) was judged too complex to safely review and ship alongside the tools above.

## Resources

The same tag data is also available through the `tags` tool, which is what a client without resource support - like the nuru CLI - can actually call.

- **`vault://tags`** (`tags`) - All unique tags (e.g. `project` for `#project`) used across notes in the vault.
- **`vault://tags/counts`** (`tag_counts`) - Occurrence counts for each unique tag across notes in the vault.

## Testing

```bash
uv run pytest
```

The semantic search tests use a stand-in embedder, so they need neither Ollama nor the model. One test checks the real `nomic-embed-text:v1.5` against the same small fixture vault, and it's skipped unless you ask for it:

```bash
OBSIDIAN_SEMANTIC_LIVE=1 uv run pytest tests/test_semantic.py -k nomic
```

See the [servers README](../README.md) for running the whole repo's tests together from the root.
